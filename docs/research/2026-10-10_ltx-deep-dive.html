00Summary

LTX is a small, sharply scoped, production-grade Go library for a self-describing, checksummed, LZ4-compressed transaction file format over SQLite pages. The engineering quality is high: streaming with bounded memory on both encode and decode, a logical-content checksum that survives recompression, chained database-state checksums, and an encoder state machine that cannot emit a structurally incomplete file with a valid checksum. Adoption is real: LiteStream (14,471 stars) builds its v0.5 core on it, and the format is the backbone of fly.io’s Liteserver.

For this repository the verdict is two-sided. As a dependency of go-codec: no — wrong layer, zero overlap with go-codec’s payload-codec contract, and importing it would couple a pure serialization library to SQLite page semantics. As a design reference and as infrastructure for the wider go-cqrs-lite stack: genuinely valuable — several of its invariants are exactly the problems go-codec’s COSE/envelope layer will face if compression or framing is ever added, and any SQLite-backed event store in the go-cqrs-lite metaengine gets a battle-tested backup/replication story for free through LiteStream+LTX.

The bottom line Do not add ltx to go-codec. Do steal its invariants: checksum the logical (uncompressed) content, keep checksums non-zero and distinguishable from “unset”, and make partial writes unfinishable. If a go-cqrs-lite storage engine ever backs onto SQLite, LTX via LiteStream is the replication/backup answer to evaluate first — pending the caveats in the findings.

01What LTX is

An LTX file represents one or more SQLite transactions as a four-section stream: a fixed 100-byte header, a page block of page frames, a varint page index for random access, and a 16-byte trailer. Files form a chain: each non-snapshot file carries the database checksum before it is applied (PreApplyChecksum) and the trailer carries the checksum after, so a replica can prove contiguity by position (Pos = TXID + PostApplyChecksum) before applying.

LTX file (format v3, magic "LTX1") Header (100B) flags, page size, commit size, MinTXID..MaxTXID, timestamp, PreApplyChecksum, WAL provenance, NodeID Page block frames in ascending pgno: [pgno u32][flags u16][csize u32][LZ4-block data] terminated by a zero page header (6 zero bytes) Page index per page: varint (pgno, offset, size), zero-terminated, sized Trailer (16B) PostApplyChecksum | FileChecksum (CRC64-ISO over logical content)

Two checksum domains are kept deliberately separate. The database checksum is an order-independent XOR of per-page CRC64 values (page number mixed in, lock page excluded), chained from file to file. The file checksum is a CRC-ISO-64 over the header, the page headers and size prefixes as stored, the decompressed page data, the index, and the trailer’s post-apply field — so two valid LZ4 encodings of the same logical content produce the same file checksum. The top bit (ChecksumFlag = 1<<63) is always set on live checksums, keeping them non-zero and distinguishable from “unset”.

The public API is three streaming types — Encoder, Decoder, Compactor (merges contiguous input files into one) — plus checksum helpers and a cmd/ltx CLI (encode-db, apply, verify, dump, list). Notably, the SQLite-aware logic lives in the CLI, not the library: the core package parses SQLite’s 100-byte database header itself and never links a SQLite driver.

02What is already excellent

+
Logical checksum decoupled from compression File checksum hashes decompressed page data, so recompression never invalidates integrity. Compare: signing the compressed bytes would break the moment a codec or level changes.
+
Chained state positions, not just sequence numbers Pos = TXID + PostApplyChecksum; a replica proves it is contiguous with a file before applying it. This is the event-store “global position with proof” pattern, done at the storage layer.
+
Memory bounded in both directions Encoder spills its page index to a temp file past 1M entries (litestream #1477); decoder can stream-validate the index without retaining it, using a running hash of decoded page numbers to prove index/pages agreement (decoder.go:43-46, 132-137).
+
Unfinishable partial files The encoder is an explicit state machine with a terminal aborted state: any failed write aborts it, and Close after Cleanup refuses to emit a second end-marker plus empty index with a valid checksum (encoder.go:62-103, 346-366).
+
Dependency hygiene One dependency (lz4). No SQLite driver in the library, no cgo, go.mod at Go 1.24. The apply/encode logic that needs SQLite knowledge ships as CLI commands.
+
Real adoption and real tests LiteStream v0.5 (14,471 stars, active) depends on superfly/ltx v0.5.2 (verified in its go.mod); wjordan/syzy (LiteFS-compatible server) on v0.5.1. Golden-file, spill, and index-validation tests; full suite passes (ran 2026-10-10, 6.9s).

03Findings

Risks and design debts, ordered by impact on anyone depending on this format.

Design debt · High impact

No on-disk format version field — v2/v3 share one magic

README.md (format spec) · ltx.go:18-24 · issue trail: format v3 bump, 2025-09-16

Versions 2 and 3 both use the LTX1 magic. The spec says it plainly: “A reader cannot determine the format version from the file alone and must know it out of band.” Version 3 changed the page frame layout (6-byte header + size prefix vs 4-byte header), and the decoder disambiguates per-frame via a page-header flag that the spec itself says “is not a format version field.” For a long-lived storage format this is the single biggest liability: future format changes have no honest escape hatch, and mixed-version archives rely on side knowledge.

Lesson for go-codec go-codec already stamps Encoding() into payloads so blind stores stay self-describing. Keep it that way: any future framing or envelope in go-codec must carry a version/magic of its own — never rely on out-of-band knowledge.
Open bugs · High impact if NoChecksum mode is used

NoChecksum mode is undertested edge territory

Issues #103, #101 (filed 2026-09-17, after v0.5.3) · issue #88

Two fresh bugs landed days after the latest release: the encoder cannot produce zero-length deletion files with HeaderFlagNoChecksum (#103), and the compactor both fails on NoChecksum inputs and silently ignores mismatched input flags (#101). A third (#88): ChecksumReader returns bare 0 instead of ChecksumFlag for an empty database, breaking the “live checksums are never zero” invariant at one edge. The always-checksum path (what LiteStream exercises in production) is solid; the opt-out path is where the splinters are.

Lesson for go-codec Feature flags that weaken an invariant (like DeterministicCodec’s strictness, or RawCodec’s escape hatches) need the same property and contract tests as the mainline path — the edge mode is where bugs cluster once real users find it.
Validation gap · Medium impact

Decoder does not verify snapshot completeness

decoder.go:155 (TODO) · issue #98 (open)

The decoder never checks that a snapshot’s last decoded page equals the header’s Commit size; the encoder enforces page completeness on write (encoder.go:305-323) but the reader trusts it. A snapshot missing trailing pages still validates its checksums. Known and tracked, but open.

Sustainability · Medium impact

Single-maintainer bus factor with a dormancy precedent

git history: no commits 2023-09 → 2025-01; recent work dominated by one author

The project went quiet for ~15 months between the original LiteStream era and its revival for Liteserver, and current activity rides on essentially one maintainer (Ben Johnson). The format is documented and the code is readable enough to fork, but any deep dependency should assume upstream may pause again.

Scope boundary · Medium impact

CRC64 is corruption detection, not tamper protection — and encryption is still a proposal

checksum.go:185-188 · issue #77 (HPKE proposal, open since 2026-02)

The README sells “can be encrypted”, but the library only shapes bytes for it: per-page encryption via HPKE (RFC 9180) is an open proposal, not code. Interesting contrast with go-codec, which already ships COSE (RFC 9052) SigStructure/Encrypt0 shaping — the two libraries sit at opposite ends of the same “shape bytes for the crypto layer” idea.

Hygiene · Low impact

Committed 1.7 MB binary in the repo

dist/ltx (1,707,520 bytes, executable) · issue #93

A built CLI binary is committed at dist/ltx and .gitignore does not cover build output. Cosmetic for consumers, but it bloats clones and invites accidental staleness.

04Relevance to go-codec

As a dependency: no

Verified against go-codec’s go.mod: the dependency set is fxamacher/cbor, go-error-family, and test-only libraries; ltx appears nowhere, and nothing in the repo references superfly. The layers do not touch: go-codec serializes event payloads (CBOR/JSON/Raw + COSE structure helpers), LTX frames database pages into transactional files. Pulling ltx in would drag SQLite page semantics and an lz4 dependency into a pure serialization library for zero functional gain. This is the same reasoning that keeps go-codec dependency-minimal today.

As design reference: five transferable invariants

Pattern · Adopt if compression ever lands

Checksum the logical content, not the container bytes

encoder.go:368 (“hash the uncompressed data”) · README file-checksum section

LTX hashes page headers as stored but page data decompressed, making the checksum invariant under recompression. go-codec currently signs encoded bytes (COSE SigStructure over the codec’s output) with no compression layer, which is correct today. The moment compression or any re-encodable framing is introduced, the signed/checksummed domain must be decided deliberately — sign the logical payload and keep the compression envelope outside the signature, or accept that any re-encode invalidates.

Pattern · Cheap invariant

“Never zero” distinguished values (ChecksumFlag)

ltx.go:59-60 · checksum.go:105, 121

Setting bit 63 on every live checksum makes zero mean “unset” unambiguously and is validated on read (PreApplyChecksum&ChecksumFlag == 0 → error). If go-codec ever adds envelope checksums or sequence stamps, this trick removes an entire class of zero-value ambiguity bugs.

Pattern · Streaming robustness

Explicit encoder state machine with a terminal abort state

encoder.go:62-103 · ltx.go:62-73

go-codec’s streaming wrappers (NewCBOREncoder/NewJSONEncoder, NDJSON) are thin delegates; their correctness rests on the underlying encoder. LTX’s pattern — named states, abort on first partial write, Close-after-abort refuses to “finish” a broken stream — is the reference if go-codec ever grows its own multi-frame envelope writer where partial output is detectable.

Pattern · Memory escalation path

Spill-to-disk for unbounded accumulations

encoder.go:16-19, 37-48, 396-494 · commits #95/#97 (2026-09-10)

The encoder’s page index grows in doubling chunks (map replaced: ~4x memory savings), then spills to a temp file past 1M entries so memory stops scaling with database size. go-codec’s buffer pool (pool.go, maxPoolBufferSize) handles the small-buffer case; LTX shows the shaped escalation path for the “the thing I must accumulate is bigger than RAM” case — spill in final on-disk format and stream it back through the same write/hash path on Close.

Pattern · Proof without retention

Hash-of-sequence instead of materialized set

decoder.go:43-46, 115-137

To prove the page index names exactly the decoded pages without keeping either set, the decoder keeps a running CRC over decoded page numbers and compares it to the same hash over index entries. A neat O(1)-memory equality proof, reusable anywhere two streams must be shown to contain the same elements.

For the wider go-cqrs-lite stack: the real angle

The go-cqrs-lite metaengine runs projections over interchangeable engines including SQLite (and Turso). Every SQLite-backed store needs a backup/replication story, and that is exactly what LTX was built for: LiteStream v0.5 continuously ships WAL transactions as LTX files to object storage and restores to any point via checksum-chained compaction. A go-cqrs-lite deployment using the sqlite engine could get point-in-time restore and replica bootstrapping through LiteStream+LTX with zero custom format code. Caveat, untested here: the store’s write pattern (single-writer WAL mode, no ATTACH-heavy multi-db churn) must be LiteStream-compatible; verify against the actual engine before relying on it.
